# 仕様書｜セール価格設定リスト データ仕様

最終更新: 2026-09-04

セール価格設定リストを kintone で作るための、入力データの取得手順と各項目の出どころを
まとめたもの。ZOZO からのダウンロード操作そのもの（画面キャプチャ付き）は別の Word
マニュアルに置き、本書はデータの中身と処理仕様を扱う。

---

## 1. 全体の流れ

```
ZOZO BACK OFFICE
  ├ 売上（注文日ベース）  ─┐
  ├ 在庫分析              ─┤
  ├ 在庫（S在庫）          ─┼→ kintone 各アプリへ取り込み → セール価格設定リスト生成
  ├ セールグッズ salegoods ─┤                                    → メーカーへ送信
  └ 商品マスタ goods      ─┘
```

---

## 2. データの取得

ZOZO BACK OFFICE から以下をダウンロードする。操作画面は Word マニュアルを参照。

### 2-1. 売上（注文日ベース）

| 項目 | 内容 |
|---|---|
| 場所 | 分析 > 売上集計（`to.zozo.jp/to/Sales.asp?c=SalesSummary`） |
| 条件 | ショップ = FUNALIVE / ベース = 売上 +「日計で表示する」チェック / 注文CSV = 注文番号なし |
| 期間 | **前回セール開始日 〜 リスト作成日の月曜日** |

期間は毎週月曜にこの範囲を毎回取り直す。前回セール開始日が回ごとに変動するため、
差分ではなく毎回フルで取る。

### 2-2. 在庫分析

| 項目 | 内容 |
|---|---|
| 場所 | 分析 > 在庫分析データ（`StockAnalysis.asp?c=init`） |
| 必須設定 | **「最終入荷日」と「お気に入り登録数」の "表示する" にチェック** |
| その他 | ショップ指定なし / お気に入り登録数の期間指定はしない（＝直近30日）/ 他はデフォルト |

### 2-3. 在庫（S在庫）

| 項目 | 内容 |
|---|---|
| 場所 | 分析 > 在庫（`zaiko_csv2.asp?c=Zaiko`） |
| 条件 | 全項目デフォルトのまま（表示全店・指定なし・抽出形式 SKU毎） |

### 2-4. セールグッズ（前回のセール価格設定内容）

| 項目 | 内容 |
|---|---|
| 場所 | 商品管理 > セール設定 > セール予約確認（`SaleSettingRegist_Tenant.asp`） |
| 条件 | ラジオボタンはデフォルトのまま検索 → 一覧から CSV ダウンロード |

**絞り込みは一切できない。** 現在登録中のセールしか表示されず、セールが未登録の間は
0件でダウンロード項目自体が出ない。**次回のセールを設定すると前回分は消えるので、
消える前に取ること。**

## 4. 各ファイルの構造

検証に使ったデータ：
`260904-kintone動作確認\セール情報設定リスト 二期間分\セール情報設定リスト202608089～202608219\0803\`

| ファイル | 行数 | 粒度 | キー |
|---|---|---|---|
| `商品マスタ_goods_20260803.csv` | 53,515 | 商品コード | ブランド品番 / 商品コード |
| `S在庫_S20260803.csv` | 132,201 | SKU | CS品番（重複なし） |
| `在庫分析_20260803.csv` | 142,979 | SKU | CS品番（重複なし） |
| `前回セール情報_salegoods_20260803.csv` | 23,491 | 商品コード | ブランド品番 / 商品コード |
| `S売上(セール成績)_20260803.csv` | — | SKU | CS品番 |

文字コードは全ファイル CP932。

### 在庫分析の注意点

- **`最終入荷日` に `-` が入る行がある。**日付型で読み込むとエラーになるため、
  **文字列として読み込むこと。**実測（`在庫分析_20260803.csv`・142,979行）では
  **92行**が該当し、**`-` が入るのは30列中この1列だけ**（`最終入荷日からの経過日数` には
  入らない）。内訳は `YUASA4 select / mizutori` 90件、`BF2 select` 1件、`Ree＆Mee` 1件で、
  **1ブランドに集中する**ため、そのメーカーの回だけ壊れて見える。
  `最終入荷日` は出力23列（A〜W）に含まれないので、文字列で持って支障はない。
- ヘッダーおよび値の先頭に半角スペースが入る列がある（` 親カテゴリ` など）。読み込み時に trim する。
  **在庫分析だけの特徴**で、他の3ファイルには無い（§4-1）。

### 4-1. ZOZO の素のファイルのヘッダー（2026-09-05 実測）

**素のZOZOファイルは、列名がそのまま kintone のフィールド名と一致する。変換表は要らない。**
kintone 側のフィールドが ZOZO の CSV に合わせて作られているため。

実物で確認したのは以下の2本。

| ファイル | 実物 | 列数 | 先頭空白 | 列名 |
|---|---|---|---|---|
| 在庫分析 | `260901-kintone商品マスタ更新\zozo-20260905在庫分析.csv` | 30 | **29 / 30列** | **一致** |
| S在庫 | `260901-kintone商品マスタ更新\zozo-在庫S20260901.csv` | 19 | 0 | **一致** |
| salegoods | 未確認 | | | |
| 売上 | 未確認 | | | |

共通仕様: CP932（Shift_JIS）/ BOM なし / 改行 CRLF / ヘッダー行に引用符なし
（データ行は文字列のみ引用符、数値は裸）。

#### 唯一の落とし穴：在庫分析の先頭スペース

在庫分析だけ `ショップ, 親カテゴリ, 子カテゴリ, ...` とカンマの後に半角スペースが入る。
つまり **1列目以外は列名の先頭に半角スペースを含む**。kintone の自動対応付けは完全一致なので、
これがあると1列目の「ショップ」しか紐づかない。

**取り込み前に必要な処理は、この先頭スペースの除去だけ。**S在庫にはスペースが無い。

#### 括弧の全角・半角が混在している

S在庫の中で `販売価格(税抜)` は**半角括弧**、`合計金額（税抜）` と `プロパー価格（税抜）` は
**全角括弧**。ZOZO 側の不統一で、kintone のフィールド名もそれに合わせてある。
**手で打ち直すと必ず間違える。**

#### 不一致の原因は担当者による書き換え

0803 のファイルは列名が旧システム寄りの用語に書き換えられていた。前後のダウンロード
（2025-12-01 / 2026-06-03 / 2026-08-25 / 2026-09-05）はすべて素の名前なので、
**ZOZO の仕様変更ではない。**`sale処理.xlsm` に合わせて手で直したものと見られる。

| | ZOZO の素 | 0803（書き換え後） |
|---|---|---|
| 在庫分析 4,5列 | 親商品タイプ / 子商品タイプ | 親タイプ / 子タイプ |
| 在庫分析 13,14列 | プロパー価格（税抜）/ 販売価格（税抜） | 上代 / 現在価格 |
| S在庫 2,3,4列 | 親カテゴリ / 子カテゴリ / 子商品タイプ | 親カテゴリー / カテゴリー / 商品タイプ |
| S在庫 14,15列 | 合計金額（税抜）/ プロパー価格（税抜） | 合計金額 / 元上代 |

**これが §12-3-2 の価格列取り違えの根本原因。**素のまま取り込めば全列が自動で紐づき、
手動マッピングそのものが発生しなかった。

#### 運用ルール

1. **ZOZO の CSV のヘッダーは編集しない。**これが最も効く
2. 在庫分析だけ、取り込み前に先頭スペースを除去する。分割ツール
   `csv_splitter_gui.py` の `split_csv` がヘッダーを `fout.write(header_bytes)` で
   素通ししているので、ここに入れるのが自然。全ファイルが必ず通るため取りこぼさない
3. あわせて、変換後のヘッダーを kintone のフィールド名一覧と照合し、
   一致しない列があれば警告して止める。ZOZO 側が列名を変えたときに気づける
4. 取り込みの対応付け画面で「(指定しない)」が1つでも残っていたら、そこで止める
5. salegoods と売上は素のファイルが未確認。次回ダウンロード時に同じ確認をする

## 6. 在庫数の仕様

### 6-1. 決定事項

**在庫数は S在庫の `在庫数`（L列）を正とする。今後はこれのみを使う。**

在庫分析の `販売可能数` / `販売可能数合計` は採用しない。
新テンプレートでも `販売可能数` の列は廃止され、在庫は1列だけになった（§9参照）。

### 6-2. 在庫分析の列の関係（全142,979行で例外ゼロ）

```
販売可能数合計 = 販売可能数 + 販売開始前点数 + 販売前予約受付数
```

この3列が食い違う行は1,959行（1.4%）。販売開始前点数>0 が1,765行、販売前予約受付数>0 が264行。

### 6-3. S在庫の在庫数と在庫分析の差 ＝ 引当（注文済み・未出荷）

両ファイルは同一スナップショット（基準日はどちらも 2026/8/3）。共通するCS品番131,710件で
`在庫数 == 販売可能数合計` は 124,372件（94.4%）、差>0 が7,100件。

差が出る行だけ直前に売れている。

| | 前日販売数>0の割合 | 直近7日 平均 | 直近30日 平均 |
|---|---|---|---|
| 差>0（7,100件） | **61.8%** | 1.70 | 4.67 |
| 一致（124,372件） | **0.1%** | 0.03 | 0.26 |

差の大きさも販売数の範囲に収まる。

```
差 == 前日販売数      : 51.7%
差 == 直近7日販売数   : 71.2%
差 <= 直近7日販売数   : 93.7%
差 <= 直近30日販売数  : 99.3%
```

**S在庫の在庫数は引当分を引いていない。在庫分析の販売可能数は引いた後。**

例外47件は直近30日販売数=0なのに差が1ある長期在庫。返品保留や不良品扱いの可能性があるが、
データからは判定できない。

### 6-4. 価格は完全一致

共通131,710件で `価格タイプ` の不一致0件、S在庫 `販売価格(税抜)` と 在庫分析 `現在価格` の
不一致0件。両ファイルでズレているのは在庫数だけ。

## 7. 対象品番の母集団と抽出条件

### 7-1. リストに載せる品番の抽出条件

**`goods.csv` のブランド品番のうち、S在庫に在庫があるものだけをリストに載せる。**

| | 件数 |
|---|---|
| goods.csv 全ブランド品番 | 53,515 |
| うち **S在庫に存在**（＝在庫がある） | **25,078** |
| 実際の送信リストのブランド品番 | 25,051 |
| 両者の一致 | **25,038（99.95%）** |

差はS在庫側に40品番、リスト側に13品番のみ。goods は廃番も含む全品番マスタで
半数以上（53.1%）は在庫がないため、この絞り込みが必要。

### 7-2. CS品番（SKU）レベルの差

リストの粒度はブランド品番単位のため、CS品番の差はブランド品番単位で見る必要がある。

CS品番は **S在庫を正とする**（132,201件）。

| | 件数 | ブランド品番単位で見ると |
|---|---|---|
| 共通 | 131,710 | — |
| S在庫のみ | 491 | ブランド品番ごと在庫分析に無いのは **83品番** |
| 在庫分析のみ | 11,269 | うち在庫あり540件。ブランド品番ごとS在庫に無いのは **13品番** |

- S在庫には **在庫数=0 の行が1件も存在しない**（在庫分析は13,290件が0）。
- 在庫分析にしか無い540件のうち **505件（93.5%）はブランド品番自体がS在庫に存在する**。
  その品番の行はリストに出るので、影響はそのSKU分の在庫数だけ。在庫をS在庫と定義した以上、
  これは正しい挙動。
- S在庫にしか無い491件のうち、ブランド品番ごと在庫分析に無いのは83品番。この83品番は
  実績列（S/U/V/W）が取れない。**→ 0埋めする（§12-1 決着済み）**

### 7-3. 「メーカー在庫状況」は抽出条件に使えない（2026-09-05 実測）

商品マスタに `メーカー在庫状況`（在庫あり／在庫切れ）があるが、**ZOZOの実在庫とは一致しない。**
手入力の管理項目のため。メーカー2の832ブランド品番で検証した。

| キントーンのみ 719品番 | 件数 | 割合 |
|---|---|---|
| 全SKUが「在庫切れ」 | 447 | 62.2% |
| 「在庫あり」と「在庫切れ」が混在 | 175 | 24.3% |
| **全SKUが「在庫あり」** | **97** | **13.5%** |

| 共通＝旧にもある 113品番 | 件数 |
|---|---|
| 全SKUが「在庫あり」 | 76 |
| 混在 | 29 |
| **全SKUが「在庫切れ」** | **8** |

| 判定基準 | 719件の切り分け | 113件への影響 |
|---|---|---|
| メーカー在庫状況＝在庫切れ | 447件しか落とせない（**272件残る**） | **8件を誤って落とす** |
| **S在庫の在庫数>0** | **719件すべて落ちる** | **1件も落ちない** |

**719品番はすべて S在庫にブランド品番ごと存在しない。**在庫数0の行があるのでもない。
「在庫あり」なのにS在庫に無い97品番も、ブランド品番ごと存在しなかった。

**データを落とす日が必ず前回セールの期間中だから。**8/3 は 8/1〜8/7 のセール中、

持たないため、その瞬間はセール価格になっている。**セール終了後に落とせば通常価格に戻る。**

#### 例外2件の理由 — セールがまだ始まっていなかった

- **プロパー行102件** — 値下げ**前**に定価で売れた明細。現在価格と違って当然

  残る `FNE-AP24089` はセール1,809・再販売5,900に対し実売2,445でどちらとも違う

#### 計算式

```
M 直近セール価格（税込み） = IF(K3="","",ROUND(K3+K3*0.1,0))

R セール価格（税抜き）
  = ROUND( IF(NOT(N3=""), ROUND(H3-H3*ROUND(N3,3),0),
           IF(NOT(O3=""), O3/1.1,
                          H3)), 0)

Q セール価格（税込み） = IF(R3="","",ROUND(R3+R3*0.1,0))

P オフ率 = IF(OR($R3="",$H3=$R3),"",
             ROUNDDOWN(1-($Q3/ROUND(($H3*1.1),0)),3))
```

N（オフ率）が優先。N が空なら O（税込価格）。どちらも空ならプロパー価格 H のまま。
消費税率は数式に 10% がハードコードされている。

### 9-4. テンプレートの行数とフィルタ範囲（2026-09-04 対応）

新テンプレートの実体は Google スプレッドシート **「セール価格設定リストテンプレート」**。
kintone の JS がこれを読み込み、コピーして Google ドライブに各メーカー分を出力する。

https://docs.google.com/spreadsheets/d/1B4Zv20QQbQyFauUcrfl6tf0QrrP-ah7TeV-BEHHn8rA/

#### 判明した問題

**出力ファイルのフィルタ範囲が全件 `A2:AG3` で固定されていた。**
無作為25件と1,316行の大口ファイルを調べて全件同じ。60行のファイルでも1,316行のファイルでも
**3行目までしかフィルタが効いていない**。テンプレート側のフィルタ範囲（2〜3行目）が
そのままコピーされ、データ行が追加されても広がっていなかった。

#### 実測した行数（`送信` フォルダの .xlsx／3期間・620ファイル）

| セール期間 | 件数 | 最大行 | 中央値 | 1000行超 |
|---|---|---|---|---|
| 2026/08/01〜08/07 | 206 | 1,292 | 59 | 3件 |
| 2026/08/08〜08/21 | 206 | 1,316 | 60 | 3件 |
| 2026/08/22〜09/04 | 208 | 1,267 | 61 | 3件 |

行数が突出しているのは毎回同じ3社（00096 アリエス様 / 00219 FINE様 / 00027 メンズ・サンエー様）。
他は中央値60行程度。

**出力ファイルに空行は一切ない**（行要素数＝最大行番号）。書き込み側がデータ行数ぴったりに
行を削除して揃えている。したがってテンプレートの行数を増やしても、空行が出力に残ることはない。

#### 対応

- テンプレートを **1,000行 → 2,000行** に拡張。Q列・R列の数式と書式も2,000行目まで複製
- フィルタを **`A2:W2000`** で作り直し

#### 注意：列全体（`A:W`）指定は使えない

このテンプレートは1行目がグループ見出し（結合セル）、2行目が実際の列名という2段ヘッダー。
列全体でフィルタを作ると**フィルタボタンが1行目に付いてしまい、フィルタとして機能しない**。
範囲は必ず2行目始まり（`A2:W○○`）で指定すること。

#### 実地確認の結果（2026-09-04〜05）

メーカー2で出力した .xlsx を調べた。

```xml
<autoFilter ref="$A$2:$W$2000"/>
<definedName name="_xlnm._FilterDatabase">'セール価格設定リスト'!$A$2:$W$2000</definedName>
```

従来の `A2:AG3` 固定は再現せず、W列より右にも広がっていない。**テンプレートの修正は効いている。**

ただし旧システムの出力と1点違う。**データは3〜834行目（832行）で、835〜2000行が空のまま残る。**
M〜R列の数式も2,000行目まで入ったままで、フィルタ範囲に空行1,166行が含まれる。
旧システムの出力に空行が無いのは、書き込み側がデータ行数ぴったりに行を削除しているため。

#### そもそもフィルタは必要か（2026-09-05 実測）

**旧システムの送信ファイル206件すべてで `autoFilter ref` は `A2:AG3` だった。**
ヘッダー行＋データ1行しか範囲に入っておらず、**フィルタは実質機能していなかった**。
115行のファイルも472行のファイルも同じ。この状態で運用が回っていたので、
機能としての必要性は確認できていない。

現状（`A2:W2000`）は「効くが範囲が広すぎる」状態で、並べ替えると空行が混ざる。
旧の `A2:AG3`（機能しないが無害）より扱いが悪い。取りうる案は3つ。

| 案 | 内容 | 評価 |
|---|---|---|
| A | データ行数に合わせて貼り直す | 正しく機能する。実装は関数1つ |
| B | テンプレートからフィルタを外す | 範囲ズレの問題が根本から消える。旧の実態とも整合 |
| C | 現状維持 | 空行込みで残る。選ばない |

**判断材料はメーカー側にフィルタの要望・問い合わせがあったかどうか。未確認（§12-2）。**

#### 案Aを実装する場合の条件

`values:batchUpdate`（値の書き込み）とは**別のエンドポイント** `spreadsheets/{id}:batchUpdate` に
`setBasicFilter` を投げる。範囲は0始まり・終端を含まない指定。メーカー2（832行）なら
`startRowIndex:1, endRowIndex:834, startColumnIndex:0, endColumnIndex:23`。

依頼するときは以下4点を条件として添える。

1. **失敗しても処理を止めない。**現状のリトライループに素直に入れると、フィルタ設定の失敗だけで
   そのメーカーの処理（コピー作成〜エクスポート）を丸ごと4回やり直すことになる。
   `try/catch` で警告ログのみにする
2. **`spreadsheets.get` はループ外で1回だけ。**シートIDを取るためだけの呼び出しで、206社ぶん
   回すと Sheets API の毎分60回の上限に近づく。ドライブのファイルコピーはシートIDを引き継ぐ
   はずだが**要確認**（テンプレートと出力1件のシートIDを比較する）
3. **列数はハードコードせず** `excelRows[0].length` から導く。列構成の変更に追随させるため
4. **余った行の削除は別件**として切り出す。フィルタ範囲の設定だけなら副作用がない。
   行削除は入力規則や条件付き書式の範囲も縮めるため、性質が違う

**2,000行の上限にも注意。**データが1,998行を超えると数式の無い行に書き込むことになる。
実測の最大は1,316行なので当面は届かないが、ガードを入れておくとよい。

#### 案A のコード（2026-09-05 作成。上の条件4点を満たす形）

**(1) シートIDはループの外で1回だけ取る**（条件2）

```js
// 出力ループに入る前に、テンプレートのシートIDを1回だけ取得する。
// ファイルコピーはシートIDを引き継ぐ前提。引き継がない環境ならここが null のままになり、
// フィルタ設定はスキップされる（処理は止めない）。
let templateSheetId = null;
try {
  const res = await fetch(
    `https://sheets.googleapis.com/v4/spreadsheets/${TEMPLATE_SPREADSHEET_ID}?fields=sheets.properties`,
    { headers: { Authorization: `Bearer ${accessToken}` } }
  );
  if (res.ok) {
    const json = await res.json();
    const sheet = json.sheets.find(s => s.properties.title === 'セール価格設定リスト')
               || json.sheets[0];
    templateSheetId = sheet.properties.sheetId;
  } else {
    console.warn('[filter] テンプレートのシートID取得に失敗。フィルタ設定はスキップします');
  }
} catch (e) {
  console.warn('[filter] テンプレートのシートID取得で例外。スキップします', e);
}
```

**(2) フィルタを貼り直す関数**（`values:batchUpdate` とは別エンドポイント）

```js
/**
 * データ行数に合わせてオートフィルタを貼り直す。
 * 範囲は0始まり・終端を含まない。1行目=グループ見出し / 2行目=項目名 / 3行目以降=データ。
 * 失敗しても呼び出し側の処理は止めない（戻り値 false）。
 */
async function applyBasicFilter(accessToken, spreadsheetId, sheetId, dataRowCount, columnCount) {
  if (sheetId === null || sheetId === undefined) return false;
  if (!dataRowCount || !columnCount) return false;

  const url = `https://sheets.googleapis.com/v4/spreadsheets/${spreadsheetId}:batchUpdate`;
  const body = {
    requests: [
      // 既存フィルタ（テンプレの A2:W2000）をいったん外してから貼り直す
      { clearBasicFilter: { sheetId: sheetId } },
      {
        setBasicFilter: {
          filter: {
            range: {
              sheetId:          sheetId,
              startRowIndex:    1,                     // 項目名の行（2行目）から
              endRowIndex:      2 + dataRowCount,      // データ最終行まで（終端は含まない）
              startColumnIndex: 0,
              endColumnIndex:   columnCount            // 列数はハードコードしない（条件3）
            }
          }
        }
      }
    ]
  };

  const res = await fetch(url, {
    method:  'POST',
    headers: { Authorization: `Bearer ${accessToken}`, 'Content-Type': 'application/json' },
    body:    JSON.stringify(body)
  });
  if (!res.ok) {
    throw new Error(`setBasicFilter Error: ${res.status} ${await res.text()}`);
  }
  return true;
}
```

**(3) 呼び出し側**（値の書き込みが終わった直後、エクスポートの前）

```js
// 値の流し込み（既存の values:batchUpdate）が終わったあと
const columnCount = excelRows.length > 0 ? excelRows[0].length : 0;

// 2,000行テンプレートの上限ガード。超えると数式の無い行に書くことになる
if (excelRows.length > 1998) {
  console.warn(`[filter] ${fileName}: ${excelRows.length}行はテンプレートの2,000行を超えています`);
}

// ★ フィルタ設定の失敗でメーカー1社の処理を丸ごとやり直さない（条件1）。
//    既存のリトライループの中に素直に入れず、ここで握りつぶして警告だけ残す
try {
  await applyBasicFilter(accessToken, spreadsheetId, templateSheetId, excelRows.length, columnCount);
} catch (e) {
  console.warn(`[filter] ${fileName}: フィルタ設定に失敗しましたが処理は続行します`, e);
}
```

メーカー2（832行）なら `startRowIndex:1 / endRowIndex:834 / startColumnIndex:0 / endColumnIndex:23`。
**余った空行の削除は含めない**（条件4）。

なお、このコードは**案Aを採る場合のもの**。フィルタ自体が要るかは未決で、
要望が確認できなければ案B（テンプレートからフィルタを外す）のほうが安全。

```js
const recipientCcName = nameCc.filter(Boolean).join(',');   // → FA様担当者 へ
```

- 宛先種別は `セール（TO）` と `セール（CC）` の2種類しかなく、**CCの中で自社と取引先を区別できない**
- CCが複数いても全部カンマ連結され、1つの文字列になる
- **CCのメールアドレスをどこにも渡していない**（TOは名前とメールの両方を拾っている）
- その文字列を `FA様担当者`（USER_SELECT）に渡すため `CB_IJ01` で落ちる（§12-3-5）

#### 決定した設計

| 役割 | 出どころ | k/60 のフィールド |
|---|---|---|
| TO | 連絡先テーブル `セール（TO）` | ブランド連絡先担当者名 / ブランド連絡先メールアドレス（既存） |
| CC（取引先） | 連絡先テーブル `セール（CC）` | **新設**: ブランド連絡先CC担当者名 / ブランド連絡先CCメールアドレス |
| CC（自社） | **メーカーマスタの担当者（kintoneユーザー）** | FA様担当者（USER_SELECT・既存） |

**連絡先テーブルの `セール（CC）` は「取引先のCC」だけを意味する**ようにする。
自社担当者はマスタに1人持つだけなので、人手の入力は増えない。

`FA様担当者` をユーザー選択のまま使うのは理にかなっている。**kintoneユーザーなら
メールアドレスをアカウントから引ける**ため、CC（自社）用のメールフィールドが要らない。
文字列フィールドに作り替える案は取らない。

`FUN担当者ID` は基幹システムの連番（藤本1 / 大門2 / 小林3 / 大稀4 / 今野5 / 堀井8 /
終了90 / 未定80）で**kintoneのログイン名ではない**。対応表を config に持つと二重管理になるため、
**メーカーマスタ from SQL にユーザー選択フィールドを1つ追加**して直接持たせる。
同アプリは既に手入力フィールド `セールリスト出力単位` を保持できている（CSV取り込みは
列に無いフィールドを消さない）。担当者は8人なので `FUN担当者名` で絞って一括編集すれば済む。

> 採らなかった案: 宛先種別に `セール（CC・FA）` を追加して区別する。全メーカーの連絡先テーブルへ
> 自社担当者を人手で入れ直すことになり、マスタにある情報の二重管理になる。1人で回している
> 業務では維持できない。

#### 12-3-2. 在庫分析アプリで価格2列が入れ替わっている

**JS は正しい。**出力機能は在庫分析を最優先で参照しており、参照順も仕様どおり。
原因は取り込み時の列の割り当て。

在庫分析 65 の **レコード番号 574759〜674757（99,999件）で
「プロパー価格（税抜）」と「販売価格（税抜）」が入れ替わっている。**
674758〜717737（42,980件）は正しい。境界は分割ファイルの切れ目と完全に一致する。

| kintone レコード | 由来 | 状態 |
|---|---|---|
| 574759〜674757（99,999件） | `0803\split\在庫分析_20260803_split_001.csv`（データ99,999行） | **入れ替わり** |
| 674758〜717737（42,980件） | 同 `_split_002.csv`（データ42,980行） | 正しい |

境界レコードの実測（元CSVはどちらも 上代3164 / 現在価格1582）:

| レコード | CS品番 | kintone のプロパー / 販売 |
|---|---|---|
| 674757 | SCL-011-3207-81-4L（split_001 の最終行） | **1582 / 3164** |
| 674758 | SCL-011-3207-81-5L（split_002 の先頭行） | 3164 / 1582 |

**原因**: 0803 の在庫分析CSVのヘッダーは `上代` / `現在価格` で、kintone のフィールド名
（プロパー価格（税抜）/ 販売価格（税抜））と一致しない。取り込み時に列の割り当てを手で
行う必要があり、**1本目のファイルでこの2列を取り違えた**。2本目では正しく割り当てている。

**この列名の不一致は ZOZO の仕様ではなく、担当者がファイルを書き換えたことによる（§4-1）。**
素の ZOZO ファイルは列名が kintone のフィールド名と一致しており、そのまま取り込めば
全列が自動で紐づく。つまり**手動マッピングそのものが発生しなかった**。

**対応**: 在庫分析の洗い替え（§3）。**再突合のために入れ直すのは 0825 ではなく 0803 のファイル。**
分割して取り込むときは **2本目以降も列の割り当てを毎回確認する。**

> 在庫 64 は同じ条件（列名が `販売価格(税抜)` / `元上代` で不一致、2分割）だが、境界レコード
> 231954／231955 の実測で**両ファイルとも正しく割り当てられている**ことを確認済み。

#### 12-3-4. 受注数・売上額の絞り込み期間

**メーカー2の出力832行のうち、受注数>0 の行は0行。**旧システムは113行中1行に
受注数1／売上額6,320 が入る。1品番の誤差ではなく**構造的に全行0**で、メーカー2は
たまたま実績が1件しかなかったため差が1件に見えていた。

JS は売上を**今回のセール期間**で絞っている。

```js
const salesQuery = `注文日 >= "${saleStartDate}" and 注文日 <= "${saleEndDate}"`;
```

`saleStartDate` / `saleEndDate` はセール設定レコードの「セール開始日／終了日」＝
今回のセール（20260808〜20260821）。一方、売上ファイルの注文日は
**20260801〜20260803 の3日分**（8,328行）。ダウンロード期間が「前回セール開始日〜
リスト作成日の月曜日」だから（§2-1）。**今回セール期間の条件では1行も該当しない。**

I列・J列は「**直近セール**の受注数・売上額」＝**前回セール**の実績。今回のセール期間で
絞るのは条件が逆になっている。

`MEI-000-205014` の例: 注文日 20260801。salegoods の前回セールは
セール開始 2026/8/1 8:45 〜 タイムセール終了 2026/8/7 9:00 で、注文はこの中に入っている。
kintone のレコード（k/76 レコード番号 207604）は 注文数1／合計金額（税抜）6320／
価格タイプ セール で正しく入っており、**データではなく条件の問題**。

**修正案は2つ。どちらにするかは未決（§12-2-5）。**

| 案 | 内容 | 備考 |
|---|---|---|
| A | 日付の絞り込みを外す | 売上ファイル自体が前回セール実績なので素直。**洗い替え運用が前提** |
| B | 前回セール期間で絞る | salegoods の `セール開始予定日時`〜`タイムセール終了日時`。洗い替え漏れがあっても正しい |

**フリーズの心配はない。**日付条件を外すと全8,328件の取得になるが、`getAllRecords` は
500件/回なので17リクエスト。コード上のコメントが言う「フリーズ」は**品番の in 句**で
クエリ文字列が肥大化する話であり、日付条件を外しても in 句は復活しない。

> **過去の突合の「受注数100%一致」は、両方0だったための一致を含む。**
> 再突合ではゼロ同士の一致を一致と数えない集計にすること。

#### 12-3-5. 宛先まわり（7〜9）

2026-09-05 にメーカー9（ガレージ）で実行して発覚した。**突合の数字には出ない。**
メーカー2・9とも属性の不一致は0件だが、セール返答表 k/60 の連絡先3列は**すべて空**だった。

**7. FA様担当者が USER_SELECT なのに文字列を渡している。**値が入った瞬間に
`[400] CB_IJ01 不正なJSON文字列です` で一括登録が落ちる。連絡先が空のうちは
`clean()` が null を返してキーごと除外されるため発現しない。設計は §11-7。

**8. CC（取引先）の行き先が無い。**CCは担当者名しか拾っておらず、メールアドレスは
どこにも渡らない。自社CCと取引先CCの区別もできない。設計は §11-7。

**9. 親カテゴリ単位のファイル分割が未実装。**§11-4 に「ブランド（親カテゴリ）ごとに
Excel を作成」「1ブランド 1レコード 1添付ファイル」と明記されているが、groupKey が
出力単位に関わらずメーカー単位になる。

```js
const mId = parentCategoryRecord?.['メーカーID']?.value || makerCode;
const groupKey = outputUnit === 'メーカー' ? mId : makerCode;   // どちらもメーカー単位
```

親カテゴリマスタに `メーカーID` フィールドが無いため mId は makerCode に落ち、そもそも
groupKey に親カテゴリコードが入っていない。**1メーカーから複数ファイルは出ない。**

メーカー9は `セールリスト出力単位 = 親カテゴリ` に設定されており（2026-09-05 実測）、
親カテゴリが7つ・うち4つに別々の宛先が登録されている。それでも出力は
`9_Garageroom様_...xlsx` の1ファイルだけだった。旧システムが4ファイルに分けていたのは
**送信先が違うから**で、分割は見た目の都合ではない。
**複数ある親カテゴリのうち最初の1つの宛先しか付かず、残りは捨てられる。**

> 当初「出力単位がメーカーマスタから読めていない」ことを疑ったが、メーカー9は実際に
> 「親カテゴリ」設定だった。ファイル名が親カテゴリ名になるのは設定どおりの挙動。
> 判定するなら、メーカー9を一時的に「メーカー」に変えて実行し、ファイル名が
> `9_株式会社 ガレージ様_` になるかを見る（未実施）。
